1 文档概述
1.1 编写目的
本文档定义基于 QT/C++ 与 Python 混合架构的产线自动化测试框架的分层设计、职责边界、技术选型与交互规则，为框架开发、维护与扩展提供统一的设计依据，保障系统在量产场景下的稳定性、可追溯性与合规性。
1.2 核心设计三原则
QT 唯一主控原则：流程调度、硬件管控、结果判定、数据归档全由 QT 统一负责，是系统稳定的基石。
Python 插件化原则：Python 仅承担「算法计算、设备代理、报表辅助」三类扩展职责，不碰核心流程，故障进程级隔离，崩溃不影响主系统。
Excel 单一入口原则：所有测试工步、参数、阈值仅由 QT 解析加载，Python 全程不接触业务配置文件，避免文件冲突与流程失控。
2 整体架构总览
框架采用五层单向依赖架构，严格遵循「高内聚、低耦合、单向调用、跨层不可直接访问」的工业软件设计原则，上层仅能调用相邻下层的接口，底层感知不到上层存在，从架构上保障系统稳定性与可维护性。

3 各层详细设计
3.1 界面交互层（UI Layer）
3.1.1 定位
产线操作员、工艺工程师、质量人员的唯一操作入口，仅负责「展示状态、接收指令、权限管控」，不承载任何业务逻辑、测试算法与硬件控制，保证界面卡顿不会影响测试执行。
3.1.2 核心职责
测试流程控制：提供开始、暂停、停止、急停按钮，支持扫码启动测试，高危操作带二次确认防误触。
实时状态可视化：展示当前执行工步、进度条、实时测量值、Pass/Fail 计数、测试节拍、设备连接状态。
数据可视化：示波器实时波形、RF 频谱曲线、电压电流趋势图，支持缩放、定格、截图保存。
结果查询与追溯：按产品序列号、时间段、测试结果查询历史记录，支持查看原始测试详情。
权限分级管控：三级权限体系对应产线不同角色
操作员：仅能启动 / 停止测试、查看结果，无法修改用例与配置
工艺工程师：可编辑测试用例、调整阈值、校准设备
管理员：可修改系统配置、管理用户、升级程序
异常告警提示：设备离线、测试失败、校准超期、安全触发等场景弹窗 + 声光告警。

所有参数修改、用例切换均留操作日志，满足 IATF 16949 审计要求。
3.2 核心引擎层（Core Engine Layer）
3.2.1 定位
整个测试框架的「大脑与安全底线」，100% 由 QT/C++ 实现，是系统稳定性的核心保障；全权负责测试流程调度、安全联锁、结果判定、数据归档，所有业务规则在此收敛，绝不把核心控制权下放给插件层。
3.2.2 核心职责
用例与配置管理
解析 Excel 三 Sheet 结构，校验格式合法性、版本一致性。
加载设备映射、校验校准有效期，超期设备自动禁用。
用例内存结构化存储，支持按产品型号快速切换。
测试任务调度引擎
工步顺序执行、分支跳转、失败重试、超时中断全逻辑实现。
有限状态机管理系统全局状态：空闲 / 运行中 / 暂停 / 失败 / 完成 / 紧急停止。
支持多任务并行调度，多工位同时测试时资源自动仲裁。
安全联锁模块（最高优先级）
独立高优先级线程运行，不受业务逻辑阻塞。
硬实时响应急停信号、安全门信号、过压过流告警。
触发后毫秒级执行硬件下电、通道断开、测试终止动作，为产线安全红线。
结果判定引擎
统一读取 Excel 阈值，比对实测数据，输出 PASS/FAIL 判定。
支持上下限判定、区间判定、枚举值判定、自定义条件判定。
所有判定过程留痕，原始数据与判定结果绑定存储，不可篡改。
日志与审计中心
三级日志：操作日志、测试数据日志、异常故障日志。
自动记录操作人、操作时间、修改内容，满足质量体系审计要求。
日志自动按天归档，支持导出、查询。

数据与逻辑分离：测试规则来自 Excel 配置，引擎只负责执行，不硬编码业务参数，适配不同产品仅需更换用例文件。
3.3 设备抽象层（Hardware Abstraction Layer, HAL）
3.3.1 定位
屏蔽不同硬件、不同驱动方式的差异，给上层核心引擎提供统一的设备操作接口；上层引擎永远只调用标准接口，不感知底层是 QT 原生驱动还是 Python 代理驱动，实现「测试逻辑」与「硬件实现」完全解耦。
3.3.2 核心职责
统一接口定义
抽象基类IDevice定义通用能力：初始化、连接、断开、复位、发送指令、读取数据。
按设备类型派生细分接口：IPowerSupply（电源）、IOscilloscope（示波器）、IRFInstrument（射频仪）、ICanDevice（CAN）、IIoBoard（IO 板卡）等。
所有设备操作签名统一，上层调用无差异。
驱动路由与工厂管理
程序启动时读取 Excel「设备资源映射表」，根据「驱动实现方」字段自动创建对应驱动实例。
工厂模式创建设备对象，上层仅通过设备名称获取实例，无需关心底层实现。
自动路由：QT 原生驱动走内部 C++ 实现，Python 代理驱动走进程调用封装，对上层完全透明。
设备生命周期与资源管理
统一设备池管理：程序启动时一次性初始化所有设备，测试全程复用连接，避免频繁开关。
通道资源仲裁：多工步共用同一台设备时自动排队，防止资源冲突。
心跳保活与异常复位：设备断线自动重连，异常自动复位，保障长时间运行稳定性。
通道标准化映射
统一通道命名规范（PWR_CH_VCC、RF_CH_TX1、IO_DI_03），与 Excel 工步表一一对应。
屏蔽不同厂商的通道编号差异，业务层永远使用标准通道名。

校准有效期校验：设备实例创建时自动校验校准日期，超期设备强制禁用，满足合规要求。
3.4 扩展插件层（Extension Plugin Layer）
3.4.1 定位
系统的「灵活扩展区」，全部由 Python 实现，以独立脚本插件形式存在，不参与核心流程管控，仅承接单步能力输出；故障完全隔离，插件崩溃绝不影响主程序运行，是平衡「C++ 稳定性」与「Python 灵活性」的核心设计。
3.4.2 核心职责（三类插件，边界清晰）
（1）算法计算类插件（最主流、最常用）
接收 QT 传入的原始采集数据 + 配置参数，完成复杂计算后返回结果。
典型场景：
示波器波形处理：数字滤波、FFT 频谱分析、纹波峰峰值计算、上升沿 / 下降沿提取
RF 射频计算：ACLR 邻道泄漏比、EVM 误差向量幅度、功率平坦度、杂散分析
质量统计算法：CPK 过程能力指数、SPC 控制图计算、异常值剔除
特点：无状态、纯计算、输入输出完全确定。
（2）设备代理类插件（补充型）
针对无 QT/C++ 驱动、仅提供 Python SDK 的小众 / 非标设备。
接收 QT 传入的单步指令，调用厂商 SDK 操作硬件，返回采集结果。
典型场景：定制 RF 屏蔽箱、气动治具、特殊检测仪器、小众厂商设备。
特点：仅执行单步动作，不控流程、不做判定，超时、重试全由 QT 管控。
（3）报表生成类插件（辅助型）
接收 QT 汇总的批次测试数据，生成定制化分析报表。
典型场景：SPC 质量分析报告、批次不良分布统计、带波形图的失效分析报告、客户定制格式报表。
特点：仅生成文件，返回文件路径给 QT 归档展示，不修改原始数据。

3.4.4 设计要点
单插件单职责：每个功能一个独立.py 脚本，互不依赖，新增功能不影响现有插件。
无状态设计：插件不保留全局变量、不缓存数据，每次调用传入全部所需参数，避免多次调用数据串扰。
统一输入输出协议：所有插件遵循同一套 JSON IPC 规范，QT 侧通用调用逻辑，新增插件无需改调用框架。
进程级隔离：每个插件调用启动独立 Python 进程，超时 / 崩溃 / 内存泄漏均由 QT 统一销毁，绝不牵连主程序。
3.5 数据存储层（Data Persistence Layer）
3.5.1 定位
所有配置、用例、测试结果的持久化载体，兼顾「人工可读的合规存档」与「机器可读的系统对接」两类需求，是质量追溯与体系合规的基础。
3.5.2 核心职责
测试用例与配置存储
Excel 用例文件：工步、设备映射、追溯信息三 Sheet，业务人员可编辑。
系统配置文件：YAML 格式，存储全局参数、路径配置、安全阈值，工程师维护。
权限、校准记录等基础配置。
测试原始记录存储
单产品原始记录：Excel 格式，回填工步实测值、结果、时间、操作员，作为质量存档原始凭证。
结构化数据副本：JSON 格式，同一份数据的机器可读版本，用于后续分析、系统对接。
文件命名规范：产品型号_序列号_时间戳_PASS/FAIL.xlsx，分目录自动归档。
批次数据与历史库（可选）
轻量本地数据库：SQLite，存储批量测试摘要数据，支持快速查询、统计。
工厂系统对接：通过 HTTP 接口向 MES、SPC、QMS 系统上报测试结果。

自动备份：按天自动归档数据，支持定期备份到服务器，防止数据丢失。
4 层间交互规则与完整执行示例
4.1 交互铁则
仅允许自上而下调用：界面 → 核心引擎 → 设备抽象 → 扩展插件 / 存储层。
下层通过信号 / 回调向上层反馈状态，绝不主动调用上层接口。
禁止跨层直接访问：界面不能直接调硬件，必须经过核心引擎调度。
4.2 完整执行流程示例（以 RF 发射功率测试为例）
界面交互层：操作员点击「开始测试」，发出启动指令给核心引擎。
核心引擎层：校验用例版本、设备状态，从内存中取出对应工步参数，调用设备抽象层接口。
设备抽象层：根据设备名称查询路由表，识别该 RF 仪为「Python 代理驱动」，调用对应设备子类接口。
扩展插件层：设备子类内部启动 QProcess，调用 Python 驱动插件，传入 JSON 指令（频段、通道、功率等级）；Python 调用厂商 SDK 采集数据，返回 JSON 结果。
设备抽象层：接收结果，统一封装成标准数据结构返回给核心引擎。
核心引擎层：读取 Excel 阈值，比对实测功率值，判定 PASS/FAIL；记录日志、更新系统状态。
界面交互层：接收核心引擎的状态信号，刷新当前工步结果、进度条、实时数值。
数据存储层：核心引擎将该工步结果写入内存，全部工步执行完成后，统一生成 Excel 原始记录与 JSON 数据文件归档。
5 产线设计红线（不可突破）
以下职责必须牢牢掌握在 QT/C++ 侧，绝不下放给 Python，是量产场景可靠性与合规性的底线：
安全相关：急停响应、安全门检测、过流过压保护、硬件紧急下电，必须由 C++ 硬实时处理，Python 无法保障毫秒级可靠性。
流程相关：工步调度、超时控制、失败重试、分支跳转，必须由 QT 统一管控，避免脚本异常导致流程混乱。
判定相关：最终 PASS/FAIL 判定、原始测试数据归档，必须由 QT 输出，保障测试数据的权威性与可追溯性，满足 IATF 16949 审核要求。
配置相关：Excel 用例、设备配置、系统参数，只能由 QT 统一解析加载，禁止 Python 直接读取业务配置文件。
6 Excel 测试用例标准规范
Excel 是测试业务的唯一输入载体，全程仅由 QT 解析加载到内存，Python 完全不读取、不修改 Excel 文件。采用 3 核心 Sheet 结构，实现「测试逻辑、硬件配置、追溯信息」三者解耦。
6.1 Sheet 1：测试工步执行表（产线核心）
定位：程序执行的唯一依据，一行对应一个测试动作，按执行顺序排列。
核心字段：工步号、设备分类、设备名称、通道号、测试项名称、动作指令、配置参数 1/2/3、判定下限、判定上限、单位、超时 (ms)、失败处理、备注。
特点：业务人员可见可编辑，不感知底层是 QT 驱动还是 Python 驱动。
6.2 Sheet 2：设备资源映射表（工程师维护）
定位：硬件资源统一管理，实现「测试逻辑」与「硬件资源」解耦，换设备、改地址不用改动例。
核心字段：设备分类、设备名称、通道号、连接方式、地址 / 端口、设备型号、资产编号、校准有效期、驱动实现方（QT 原生 / Python 插件）、启用状态。
关键作用：QT 启动时构建路由映射，执行工步时自动选择对应驱动方式。
6.3 Sheet 3：产品追溯信息表（合规必备）
定位：满足质量体系版本管控要求，一张用例表对应一个产品型号，签字生效后受控管理。
核心字段：产品型号、用例版本号、标准测试节拍、引用标准、编制 / 批准人、生效日期、版本变更记录。
