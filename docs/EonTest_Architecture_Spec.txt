## 1. 两份设计的对比分析

### 1.1 豆包设计 (QT+Python.docx)

| 维度 | 评价 |
|------|------|
| 五层架构 | 规范，行业对标 NI TestStand / Vector CANoe |
| Excel 三 Sheet | 是量产测试的事实标准（工步表、设备映射、追溯信息） |
| QT 唯一主控 | 合理，核心流程稳定性必须 C++ 保障 |
| Python 进程隔离 | QProcess 独立进程，崩溃不牵连主程序 |
| 设备抽象层 | 工厂+多态，但写死了 Qt 原生驱动（VISA/串口） |
| **不足** | 无 workflow 分支/跳转/重试/条件逻辑；无 Python 作为完整仪器后端；QML 被否定但我们的 Studio 已是 QML |

### 1.2 TestCase_Sample.xlsx（3 Sheet）

**Sheet 1 - 测试工步表（8条样例）：**
一行=一个测试动作，包含设备名、通道号、动作指令、配置参数1/2/3、下限/上限/单位、超时、失败处理。支持多台同型设备（电源_主/电源_辅）。

**Sheet 2 - 设备资源映射表：**
设备名→连接方式/地址/型号/校准有效期/通道固有参数。实现工步与硬件解耦。

**Sheet 3 - 产品追溯信息表：**
产品型号、用例版本、测试节拍、编制/批准、IATF 16949 签字。

### 1.3 当前实现状态 (V1.1)

| 维度 | 现状 |

## 2. 最终架构设计（五层 + 原生 Excel）

```
                   ┌──────────────────────┐
                   │   Excel 三 Sheet     │  ← 工艺工程师编辑，原生格式
                   │  (TestCase.xlsx)     │     引擎直接读取，无中间格式
                   └──────────┬───────────┘
                              │ XlsxParser (PowerShell解ZIP + Qt XML解析)
                              ▼
    ┌─────────────────────────────────────────────────────────┐
    │                    WorkflowDefinition                   │
    │  (C++ 内存结构: stepId / pluginId / policy / params)    │
    └────┬────────────────────┬───────────────────┬───────────┘
         │                    │                   │
    ┌────▼───────┐   ┌───────▼─────────┐   ┌─────▼──────────┐
    │ Studio     │   │  Core Engine    │   │ InstrumentMgr  │
    │ QML UI     │   │  WorkflowEngine │   │ (仪器注册表)    │
    │ 图形编辑器  │   │  + 安全联锁     │   │ 工厂+多态       │
    │ Dashboard   │   │  + 判定引擎     │   └────┬──────────┘
    │ CELL/Log    │   └────────────────┘        │
    └─────────────┘                     ┌──────┼──────┐
                                        ▼      ▼      ▼
                                  ┌──────┐ ┌──────┐ ┌──────┐
                                  │Serial │ │QProc │ │libPy │
                                  │Backend│ │+Python│ │Backend│
                                  └──────┘ └──────┘ └──────┘
```

### 关键变更（V1.0 → V1.1）

**移除 JSON Workflow 中间格式。** 架构从：
```
Excel → 编译转换 → JSON Workflow → 引擎
```
改为：
```
Excel → XlsxParser → 引擎内存结构 (WorkflowDefinition)
```

**XlsxParser** 位于 Infrastructure 层，职责：
1. 调用 Windows PowerShell `Expand-Archive` 解压 .xlsx（ZIP 格式）
2. 用 `QXmlStreamReader` 解析 `xl/worksheets/sheet1~3.xml`
3. 从 `xl/sharedStrings.xml` 读取共享字符串表
4. 映射列：A=工步号 B=设备分类 C=设备名称 D=通道 E=测试项 F=动作指令 G~I=配置参数 J=下限 K=上限 L=单位 M=超时ms N=失败处理 O=备注
5. 设备类型 → pluginId 自动映射（电源→power.supply, 万用表→measure.voltage 等）
6. 返回 `WorkflowDefinition` 内存结构，引擎直接执行

**向后兼容：** 引擎仍可加载 `.json` 旧格式（通过 `parseWorkflowDefinitionJson`）。

```
IBackend (后端抽象)
├── open(config) → bool
├── write(data) → bool
├── readUntil(term, timeout) → QByteArray
├── readLine(timeout) → QByteArray
└── close()

InstrumentDriver (仪器驱动抽象)
├── connect(backend) → bool
├── disconnect()
├── sendCmd(cmd) → bool
├── query(cmd, timeout) → QString
└── 子类: PowerSupplyDriver, MultimeterDriver, OscilloscopeDriver, RFSignalGenDriver, CANTransceiverDriver, IODriver...
```

### 2.2 Python 集成双模式

| 模式 | 适用场景 | 实现 |
|------|---------|------|
| **QProcess + JSON IPC** | 量产产线（默认） | 独立进程，崩溃不影响主程序 |
| **libpython 内嵌** | 研发高速闭环控制 | C++ 直接调 Python，零序列化延迟 |

两种模式通过 Backend 基类多态切换，业务代码无差异。

## 5. 与豆包设计的差异总结

| 事项 | 豆包设计 | 本设计 | 理由 |
|------|---------|--------|------|
| Excel 三 Sheet | 采纳 | 采纳 | 行业标准做法 |
| Qt 主控原则 | 采纳 | 采纳 | IATF 16949 合规 |
| 五层架构 | 采纳 | 采纳 | 精简化（合并 HAL+Plugin） |
| Python 仅算法 | 不采纳 | Python 可作为完整仪器后端 | 许多仪器只有 Python SDK |
| Qt Widgets | 不采纳 | 保持 QML | 已有 Studio 投资，QML 同样可产线化 |
| 系统 YAML 配置 | 采纳 | 采纳 | libyaml 或 yaml-cpp |
| 安全联锁独立线程 | 采纳 | 采纳 | 硬件急停必须硬实时 |
| Robot Framework 兼容 | 保留 | 保留 | 作为可选研发补充 |
| 多 CELL 并行 | 未涉及 | 保留 | 已有实现 |
