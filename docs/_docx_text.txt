跨层不可 直接访问」的工业软件设计原则，上层仅能调用相邻下层的接口，底层感知不到上层存在，从架构上保障系统稳定性与可维护性。 层级 定位 实现语言 核心价值 界面交互层 用户操作入口、状态可视化 QT/C++ (Widgets) 操作防错、状态直观、权限分级 核心引擎层 系统大脑、流程与安全总控 QT/C++ 稳定可靠、流程可控、合 规 可追溯 设备抽象层 硬件统一入口、驱动屏蔽层 QT/C++ 硬件差异透明、扩展灵活、资源统一管理 扩展插件层 算法与非标能力扩展 Python 快速迭代、生态丰富、故障隔离 数据存储层 用例、结果、配置持久化 文件 + 轻量数据库 数据可追溯、合 规 存档、对接工厂系统 层间交互铁则：仅允许自上而下调用，禁止反向依赖； 禁止跨层直接 访问（如界面不能直接操作硬件，必须经过核心引擎），从架构上避免逻辑混乱与牵一发而动全身的问题。 3 各层详细设计 3.1 界面交互层（ UI Layer ） 3.1.1 定位 产线操作员 、工艺工程师、质量人员的唯一操作入口，仅负责「展示状态、接收指令、权限管控」， 不 承载任何业务逻辑、测试算法与硬件控制，保证界面卡 顿不会 影响测试执行。 3.1.2 核心职责 测试流程控制：提供开始、暂停、停止、急停按钮，支持 扫码启动 测试，高危操作带二次确认防误触。 实时状态可视化：展示当前执行工步、进度条、实时测量值、 Pass/Fail 计数、测试节拍、设备连接状态。 数据可视化：示波器实时波形、 RF 频谱曲线、电压电流趋势图，支持缩放、定格、截图保存。 结果查询与追溯：按产品序列号、时间段、测试结果查询历史记录，支持查看原始测试详情。 权限分级管控：三级权限体系 对应产线不同 角色 操作员：仅能启动 / 停止测试、查看结果，无法修改用例与配置 工艺工程师：可编辑测试用例、调整阈值、校准设备 / 暂停 / 失败 / 完成 / 紧急停止。 支持多任务并行调度，多工位同时测试时资源自动仲裁。 安全 联锁 模块（最高优先级） 独立高优先级线程运行，不受业务逻辑阻塞。 硬实时响应急停信号、安全门信号、过压过流告警。 触发后毫秒级执行硬件下电、通道断开、测试终止动作，为 产线安全红 线。 结果判定引擎 统一读取 Excel 阈值，比对实测数据，输出 PASS/FAIL 判定。 支持上下限判定、区间判定、 枚举值 判定、自定义条件判定。 所有判定过程留痕，原始数据与判定结果绑定存储，不可篡改。 日志与审计中心 三级日志：操作日志、测试数据日志、异常故障日志。 自动记录操作人、操作时间、修改内容，满足质量体系审计要求。 日志自动按天归档，支持导出、查询。 3.2.3 技术 栈 明细 功能模块 技术选型 选型说明 语言标准 C++17 / C++20 现代 C++ 特性，保障性能与可维护性 并发与线程 QThread + QTimer + 信号槽 QT 原生并发机制，成熟稳定，配合互斥 锁保证 线程安全 状态机 QStateMachine / 自 研 有限状态机 规范流程跳转，避免混乱的 if-else 逻辑 Excel 解析 QXlsx 纯原生解析，无需 Office 环境， 产线部署零 依赖 JSON 处理 nlohmann / json 核心职责 统一接口定义 抽象基类 IDevice 定义通用能力：初始化、连接、断开、复位、发送指令、读取数据。 按设备类型派生细分接口： IPowerSupply （电源）、 IOscilloscope （示波器）、 IRFInstrument （射频仪）、 ICanDevice （ CAN ）、 IIoBoard （ IO 板卡）等。 所有设备操作签名统一，上层调用无差异。 驱动路由与工厂管理 程序启动时读取 Excel 「设备资源映射表」，根据「驱动实现方」字段自动创建对应驱动实例。 工厂模式创建设备对象，上层仅通过设备名称获取实例，无需关心底层实现。 自动路由： QT 原生 驱动走 内部 C++ 实现， Python 代理 驱动走进程 调用封装，对上层完全透明。 设备生命周期与资源管理 统一设备池管理：程序启动时一次性初始化所有设备，测试全程复用连接，避免频繁开关。 通道资源仲裁： 多工步共用 同一台设备时自动排队，防止资源冲突。 心跳保活与异常复位：设备断线自动重连，异常自动复位， 保障长 时间运行稳定性。 通道标准化映射 统一通道命名规范（ PWR_CH_VCC 、 RF_CH_TX1 、 IO_DI_03 ），与 Excel 工步表 一一对应。 屏蔽不同厂商的通道编号差异，业务 层永远 使用标准通道名。 3.3.3 技术 栈 明细 功能模块 技术选型 选型说明 设计模式 抽象工厂 + 多态 经典硬件抽象实现，扩展新设备仅需新增子类，不修改上层代码 通用仪器通信 QTcpSocket + QSerialPort + VISA 封装 覆盖 LAN 、 USB 、串口、 GPIB 等主流仪器接口， SCPI 指令通用 CAN 总线 周立功 / Vector 官方 C++ SDK + 统一封装 适配主流 CAN 硬件，屏蔽厂商 API 差异 Python 代理驱动封装 QProcess + 标准 JSON 协议 把 Python 驱动封装成标准设备子类，对上层无感知 异常处理 统一错误码 + 异常分类 所有设备返回统一错误码，上层统一处理重试、停机逻辑 3.3.4 设计要点 面向接口编程：上层引擎完全依赖抽象接口，不依赖任何具体设备型号，更换同类型硬件无需修改业务代码。 设备初始化与测试流程分离：开机预热、自检在程序启动阶段完成，测试执行阶段零等待， 保障产线节拍 。 校准有效期校验：设备实例创建时自动校验校准日期，超期设备强制禁用，满足合 规 要求。 3.4 扩展插件层（ Extension Plugin Layer ） 3.4.1 定位 系统的「灵活扩展区」，全部由 Python 实现，以独立脚本插件形式存在，不参与核心流程管控，仅承接单步能力输出；故障完全隔离，插件崩溃绝不影响主程序运行，是平衡「 C++ 稳定性」与「 Python 灵活性」的核心设计。 3.4.2 核心职责（三类插件，边界清晰） （ 1 ）算法计算类插件（ 最 主流、最常用） 接收 QT 传入的原始采集数据 + 配置参数，完成复杂计算后返回结果。 典型场景： 示波器波形处理：数字滤波、 FFT 频谱分析、纹波峰峰值计算、上升沿 / 下降沿提取 RF 射频计算： ACLR 邻道泄漏比、 EVM 误差向量幅度、功率平坦度、杂散分析 质量统计算法： CPK 过程能力指数、 SPC 控制图计算、异常值剔除 特点：无状态、纯计算、输入输出完全确定。 （ 2 ）设备代理类插件（补充型） 针对无 QT/C++ 驱动、仅提供 Python SDK 的小众 / 非标设备。 接收 QT 传入的单步指令，调用厂商 SDK 操作硬件，返回采集结果。 典型场景：定制 RF 屏蔽箱、气动治具、特殊检测仪器、小众厂商设备。 特点：仅执行单步动作， 不 控流程、不做判定，超时、重试全由 QT 管控。 （ 3 ）报表生成类插件（辅助型） 接收 QT 汇总的批次测试数据，生成定制化分析报表。 典型场景： SPC 质量分析报告、批次不良分布统计、带波形图的失效分析报告、客户定制格式报表。 特点：仅生成文件，返回文件路径给 QT 归档展示，不修改原始数据。 3.4.3 技术 栈 明细 插件类型 核心依赖库 用途说明 通用算法 numpy 、 scipy 数值计算、信号滤波、 FFT 、统计分析，工业级算法精度 RF 射频 scikit-rf 、 pyvisa 射频参数计算、通用仪器程控 报表生成 pandas 、 matplotlib 、 openpyxl 数据统计、图表绘制、复杂格式 Excel 报表输出 设备驱动 厂商 Python SDK 、 pyserial 对应非标设备的驱动调用 运行环境 Python 3.10 LTS 产线优先 选用长期支持版，稳定优先，不追最新版本 3.4.4 设计要点 单插件单职责：每个功能一个独立 . py 脚本，互不依赖，新增功能不影响现有插件。 无状态设计：插件不保留全局变量、 不 缓存数据，每次调用传入全部所需参数，避免多次调用数据串扰。 统一输入输出协议：所有插件遵循同一套 JSON IPC 规范， QT 侧通用调用逻辑，新增插件无需改调用框架。 进程级隔离 ：每个插件调用启动独立 Python 进程，超时 / 崩溃 / 内存泄漏均由 QT 统一销毁，绝不牵连主程序。 3.5 数据存储层（ Data Persistence Layer ） 3.5.1 定位 所有配置、用例、测试结果的持久化载体，兼顾「人工可读的合 规 存档」与「机器可读的系统对接」两类需求，是质量追溯与体系合 规 的基础。 3.5.2 核心职责 测试用例与配置存储 Excel 用例文件：工步、设备映射、追溯信息三 Sheet ，业务人员可编辑。 系统配置文件： YAML 格式，存储全局参数、路径配置、安全阈值，工程师维护。 权限、校准记录等基础配置。 测试原始记录存储 单产品原始记录： Excel 格式， 回填工步实测 值、结果、时间、操作员，作为质量存档原始凭证。 结构化数据副本： JSON 格式，同一份数据的机器可读版本，用于后续分析、系统对接。 文件命名规范：产品型号 _ 序列号 _ 时间戳 _PASS/FAIL.xlsx ，分目录自动归档。 批次数据与历史库（可选） 轻量本地数据库： SQLite ，存储批量测试摘要数据，支持快速查询、统计。 工厂系统对接：通过 HTTP 接口向 MES 、 SPC 、 QMS 系统上报测试结果。 3.5.3 技术 栈 明细 存储类型 技术选型 选型说明 Excel 文件 QXlsx （读写） 产线零 依赖，同时支持读取用例与写入测试记录 系统配置 yaml-cpp YAML 可读性强，适合结构化配置，比 JSON 更适合人工维护 结构化数据 nlohmann / json 进程通信、数据上报、中间存储通用 轻量数据库 QSqlite （ QT 内置） 无需额外安装数据库，适合单机 产线数据 存储 系统对接 QNetworkAccessManager HTTP 接口对接 MES 、 扫码枪 、贴标机等外设 3.5.4 设计要点 原始记录不可篡改：生成后的测试文件设置只读属性，仅追加备注，不可修改原始数据，满足 IATF 16949 合 规 要求。 双副本机制：同一份测试结果同时生成 Excel 人工版 + JSON 机器版，兼顾存档与对接需求。 自动备份：按天自动归档数据，支持定期备份到服务器，防止数据丢失。 4 层间交互规则与完整执行示例 4.1 交互铁则 仅允许自上而下调用：界面 → 核心引擎 → 设备抽象 → 扩展插件 / 存储层。 下层通过信号 / 回调向上层反馈状态，绝不主动调用上层接口。 禁止跨层直接 访问：界面不能直接调硬件，必须经过核心引擎调度。 4.2 完整执行流程示例（以 RF 发射功率测试为例） 界面交互层：操作员点击「开始测试」，发出启动指令 给核心 引擎。 核心引擎层：校验用例版本、设备状态，从内存中取出 对应工步参数 ，调用设备抽象层接口。 设备抽象层：根据设备名称查询路由表，识别该 RF 仪为「 Python 代理驱动」，调用对应设备子类接口。 扩展插件层：设备子 类内部 启动 QProcess ，调用 Python 驱动插件，传入 JSON 指令（频段、通道、功率等级）； Python 调用厂商 SDK 采集数据，返回 JSON 结果。 设备抽象层：接收结果，统一封装成标准数据结构返回 给核心 引擎。 核心引擎层：读取 Excel 阈值，比对实测功率值，判定 PASS/FAIL ；记录日志、更新系统状态。 界面交互层：接收核心引擎的状态信号，刷新 当前工步结果 、进度条、实时数值。 数据存储层：核心引擎将 该工步结果 写入内存， 全部工步执行 完成后，统一生成 Excel 原始记录与 JSON 数据文件归档。 5 产线设计 红线（不可突破） 以下职责必须牢牢掌握在 QT/C++ 侧，绝不下放给 Python ，是量产场景可靠性与合 规 性的底线： 安全相关：急停响应、安全门检测、过流过压保护、硬件紧急下电，必须由 C++ 硬实时处理， Python 无法保障毫秒级可靠性。 流程相关：工步调度、超时控制、失败重试、分支跳转，必须由 QT 统一管控，避免脚本异常导致流程混乱。 判定相关：最终 PASS/FAIL 判定、原始测试数据归档，必须由 QT 输出，保障测试数据的权威性与可追溯性，满足 IATF B.3 约束与风险 内 嵌模式 下 Python 异常会 直接影响 主进程 稳定性，仅允许用于 非安全类 的实时计算场景。 必须配置独立的异常捕获机制， Python 侧崩溃立即重置运行环境，避免连带主程序崩溃。 Python 依赖版本固定，不支持现场热更新脚本。 附录 C Robot Framework 用例兼容方案 C.1 适用场景 兼容团队存量 RF 用例、通用功能回归测试场景，不纳入
