# EonTest 统一通信响应解码与测量配置架构实施方案

> 文档用途：技术方案归档、后续开发实施依据、协议插件接入规范。
>
> 适用日期：2026-07-26
>
> 适用项目：EonTest

---

## 1. 背景与目标

当前 DoIP 工步已经可以完成：

- TCP 长连接；
- DoIP Routing Activation；
- 多条 UDS 指令复用同一 TCP 通道；
- UDS TesterPresent 周期保活；
- DoIP 中间 ACK/NACK 处理；
- TCP 半包、粘包处理；
- UDS `Response Pending (0x78)` 处理；
- `expectedResponse` 完整响应匹配；
- `expectedPrefix` 响应前缀匹配。

但是当前测量结果主要还是以原始 HEX 字符串形式输出。例如：

```text
62 F1 05 0B B8
```

实际测试通常还需要：

- 从响应中截取指定字节；
- 按大端或小端解释；
- 转换为无符号整数、有符号整数；
- 转换为 `float32`、`float64`；
- 转换为 ASCII、UTF-8 字符串；
- 提取位域；
- 按比例、偏移、公式换算；
- 对换算后的工程量执行上下限判断；
- 一条响应中提取多个测量值；
- 将原始值和工程值同时写入报告、日志和 Studio。

本方案的目标是建立一个与通信接口无关的统一响应解码体系，使 DoIP、Modbus、CAN、CAN FD、RS232、RS485、TCP、UDP、LIN、I2C、USB、SPI 等接口都可以复用同一套数据提取和换算能力。

核心原则：

> 通信插件负责“收发和组帧”，协议层负责“提取有效 Payload”，通用解码器负责“截取、转换、公式和测量结果”。

新增一个 DID、寄存器、CAN 信号或串口字段时，优先修改 Excel/JSON 配置，不修改通信插件代码。

## 3. 分层职责

### 3.1 传输层

传输层只负责连接和字节收发，不解释业务含义。

示例：

- TCP socket；
- UDP datagram；
- COM 串口；
- CAN/CAN FD channel；
- LIN channel；
- I2C device；
- USB endpoint；
- SPI device。

传输层应提供类似现有 `IBusDriver` 的能力：

```cpp
bool open(const BusConfig& config, QString& errorMessage);
void close();
bool send(const BusFrame& frame, QString& errorMessage);
bool receive(BusFrame& frame, int timeoutMs, QString& errorMessage);
bool isOpen() const;
```

传输层不应处理：

- UDS DID；
- Modbus 寄存器含义；
- 温度换算；
- 公式计算；
- 测量上下限。

### 3.2 协议层

协议层负责：

1. 构造协议请求；
2. 识别帧边界；
3. 处理协议 Header；
4. 处理 ACK/NACK；
5. 处理超时和重试；
6. 处理协议级错误；
7. 输出统一的有效 Payload。

示例：

#### DoIP

```text
TCP 字节流
→ DoIP Header
→ Routing Activation / Diagnostic Message
→ 去除 DoIP Header、SourceAddress、TargetAddress
→ UDS Payload
```

#### Modbus TCP

```text
TCP 字节流
→ MBAP Header
→ UnitId / FunctionCode / Data
→ 输出有效数据区
```

#### CAN/ISO-TP

```text
CAN Frame
→ 按 CAN ID 过滤
→ ISO-TP 单帧/多帧重组
→ UDS Payload 或应用数据
```

#### RS232/RS485

```text
串口字节流
→ 按长度、终止符、CRC 或协议规则组帧
→ 输出有效数据区
```

#### LIN

```text
LIN Frame ID
→ 校验 Frame ID、校验和
→ 输出 Frame Data 或 Signal Data
```

#### I2C

```text
设备地址 + 寄存器读操作
→ 读取指定字节
→ 输出寄存器数据区
```

#### USB

```text
HID Report / CDC / Bulk Endpoint / Vendor Protocol
→ 按厂商协议组帧
→ 输出 Payload
```

### 3.3 通用解码层

通用解码器只接收已经组帧的有效数据：

```cpp
struct NormalizedResponse {
    QByteArray payload;
    QString protocol;
    QString messageName;
    quint64 messageId = 0;
    QVariantMap metadata;
};
```

通用解码器不关心数据来自 DoIP、CAN 还是 Modbus，只处理：

- 字节范围；
- 数据类型；
- 字节序；
- 位域；
- 字符串编码；
- 公式；
- 测量结果。

### 3.4 运行时与展示层

运行时负责：

- 调用协议插件；
- 调用 `ResponseDecoder`；
- 写入 `WorkflowContext.data`；
- 发布 `activity.finished` / `activity.failed`；
- 执行上下限判定；
- 保存 `step-results.jsonl`。

Studio 负责显示：

- 原始响应；
- 解码后的测量值；
- 单位；
- 测量项名称；
- 原始值与工程值；
- 公式；
- 判定结果。

## 4. 统一数据模型

建议新增以下结构。

### 4.1 解码配置

```cpp
struct DecodeSpec {
    QString name;
    int offset = 0;
    int length = -1;
    QString type = "hex";
    QString endian = "big";
    QString encoding = "ascii";
    int bitOffset = 0;
    int bitLength = 0;
    QString formula;
    QString unit;
    QString regex;
    QVariantMap metadata;
};
```

### 4.2 解码结果

```cpp
struct DecodedMeasurement {
    QString name;
    QVariant rawValue;
    QVariant value;
    QString rawHex;
    QString unit;
    QString type;
    QString formula;
    bool passed = true;
    QString errorMessage;
};
```

### 4.3 一个响应的多个测量值

```cpp
struct DecodeResult {
    QByteArray payload;
    QList<DecodedMeasurement> measurements;
    QString errorMessage;
    bool success = false;
};
```

建议保留以下上下文字段：

```text
rawResponse
rawResponseHex
measuredValue
measuredUnit
measurementName
measuredSamples
resultItems
```

其中：

- `rawResponseHex`：完整有效 Payload 的 HEX；
- `measuredValue`：单测量项的最终工程值；
- `measuredSamples`：多个测量结果；
- `resultItems`：结构化结果列表；
- `resultText`：PASS / FAIL。

## 5. 支持的数据类型

第一阶段建议实现以下类型：

| 类型 | 说明 |
|---|---|
| `hex` | 保留 HEX 字符串 |
| `uint8` | 1 字节无符号整数 |
| `uint16` | 2 字节无符号整数 |
| `uint32` | 4 字节无符号整数 |
| `uint64` | 8 字节无符号整数 |
| `int8` | 1 字节有符号整数 |
| `int16` | 2 字节有符号整数 |
| `int32` | 4 字节有符号整数 |
| `int64` | 8 字节有符号整数 |
| `float32` | IEEE 754 单精度浮点数 |
| `float64` | IEEE 754 双精度浮点数 |
| `string` | 按 encoding 解码 |
| `bits` | 位域转换为整数 |

兼容简写：

```text
uint  -> 根据 length 选择 uint8/16/32/64
int   -> 根据 length 选择 int8/16/32/64
float -> 默认 float32
```

类型检查规则：

- `offset >= 0`；
- `length > 0`；
- `offset + length <= payload.size()`；
- 整数长度不能超过 8；
- `float32` 必须为 4 字节；
- `float64` 必须为 8 字节；
- `bits` 必须满足 `bitOffset >= 0`、`bitLength > 0`；
- 解码失败必须返回明确错误，不得静默输出 0。

## 6. 字节截取规则

统一使用 0-based offset。

例如 UDS 响应：

```text
62 F1 05 0B B8
```

下标：

```text
62  F1  05  0B  B8
0   1   2   3   4
```

提取 `0B B8`：

```text
valueOffset=3
valueLength=2
```

注意：offset 相对于协议层输出的 Payload，而不是完整传输帧。

完整 DoIP 帧：

```text
DoIP Header + TargetAddress + SourceAddress + UDS Payload
```

DoIP 协议层应先输出：

```text
UDS Payload = 62 F1 05 0B B8
```

然后解码器才使用 `valueOffset=3`。

---

## 7. 字节序规则

支持：

```text
endian=big
endian=little
```

示例：

```text
0B B8
```

大端：

```text
0x0BB8 = 3000
```

小端：

```text
0xB80B = 47115
```

默认值建议为：

```text
endian=big
```

协议插件可以在协议规范明确要求时提供默认值，但 Excel/JSON 中显式配置优先级更高。

## 8. 字符串和正则提取

### 8.1 ASCII

```text
valueOffset=3,
valueLength=12,
valueType=string,
encoding=ascii
```

### 8.2 UTF-8

```text
valueOffset=3,
valueLength=20,
valueType=string,
encoding=utf8
```

### 8.3 去除尾部填充

字符串解码后应支持移除：

- `0x00`；
- 空格；
- `0xFF`。

建议配置：

```text
trim=true
padding=00
```

### 8.4 ASCII 文本中的数字

例如：

```text
TEMP=25.6;VOLT=12.3\r\n
```

配置：

```text
valueType=string,
extractRegex=TEMP=([+-]?[0-9.]+),
postType=float64
```

正则必须限制在数据字符串上执行，不允许执行脚本。

## 9. 位域提取

例如数据：

```text
62 F1 20 35
```

从 `0x35` 的 bit2 开始取 3 位：

```text
valueOffset=3,
valueLength=1,
valueType=bits,
bitOffset=2,
bitLength=3
```

建议明确 bit 编号规则：

- `bitOffset=0` 表示最低有效位 LSB；
- `bitLength` 表示连续位数；
- 位域结果按无符号整数输出。

如协议使用 MSB 方向，应增加：

```text
bitOrder=msb
```

默认：

```text
bitOrder=lsb
```

## 10. 公式计算

公式输入统一使用变量：

```text
x
```

### 10.1 基础公式

```text
formula=x/4
formula=x*0.1-40
formula=(x*0.01)-40
formula=abs(x)
```

### 10.2 典型场景

原始值：

```text
0B B8 = 3000
```

转速：

```text
formula=x/4
```

结果：

```text
750 rpm
```

温度：

```text
formula=x*0.1-40
```

结果：

```text
实际温度 = 原始值 × 0.1 - 40
```

### 10.3 公式安全要求

公式引擎只能允许：

- 数字常量；
- `x`；
- `+ - * / %`；
- 括号；
- `abs`、`min`、`max`、`round`；
- 必要时增加 `floor`、`ceil`。

禁止：

- 文件访问；
- 网络访问；
- 任意脚本执行；
- 系统命令；
- Qt 对象访问；
- 反射或动态加载。

建议第一阶段实现一个小型表达式解析器，不直接开放任意 JavaScript 引擎。

除零、溢出、非法字符、结果非有限值必须返回错误。

## 11. 单测量项 Excel 配置

### 11.1 DoIP 转速示例

假设响应：

```text
62 F1 05 0B B8
```

Excel 配置参数：

```text
udsPayload=22 F1 05,expectedPrefix=62 F1 05,valueOffset=3,valueLength=2,valueType=uint16,endian=big,formula=x/4
```

Excel 字段：

| 字段 | 值 |
|---|---|
| 测试项名称 | 发动机转速 |
| 配置参数1 | 上述配置 |
| 下限值 | 0 |
| 上限值 | 8000 |
| 单位 | rpm |

结果：

```text
RawValue = 3000
MeasuredValue = 750
Unit = rpm
```

### 11.2 DoIP 软件版本字符串

```text
udsPayload=22 F1 87,expectedPrefix=62 F1 87,valueOffset=3,valueType=string,encoding=ascii,trim=true
```

### 11.3 Modbus 示例

如果协议层输出：

```text
0B B8
```

配置：

```text
valueOffset=0,valueLength=2,valueType=uint16,endian=big,formula=x/4
```

如果协议层输出仍包含功能码：

```text
03 0B B8
```

配置：

```text
valueOffset=1,valueLength=2,valueType=uint16,endian=big,formula=x/4
```

推荐协议层尽量输出有效数据区，避免每个业务工步重复处理协议 Header。

### 11.4 CAN 示例

CAN ID `0x321`，数据：

```text
0B B8 00 64
```

协议过滤配置：

```text
messageId=0x321
```

测量配置：

```text
valueOffset=0,valueLength=2,valueType=uint16,endian=big,formula=x/4,unit=rpm
```

### 11.5 RS232/RS485 示例

ASCII 响应：

```text
TEMP=25.6;VOLT=12.3\r\n
```

配置：

```text
valueType=string,extractRegex=TEMP=([+-]?[0-9.]+),postType=float64,unit=°C
```

## 12. 多测量项配置

一条响应包含多个字段时，不应发送多次相同请求。应支持一个响应配置多个测量项。

### 12.1 JSON 解码配置

Excel 中建议只引用文件：

```text
udsPayload=22 F1 30,expectedPrefix=62 F1 30,decodeProfile=DoIP_DID_F130.json
```

文件内容：

```json
{
  "measurements": [
    {
      "name": "转速",
      "offset": 3,
      "length": 2,
      "type": "uint16",
      "endian": "big",
      "formula": "x/4",
      "unit": "rpm"
    },
    {
      "name": "温度",
      "offset": 5,
      "length": 2,
      "type": "uint16",
      "endian": "big",
      "formula": "x*0.1-40",
      "unit": "°C"
    }
  ]
}
```

### 12.2 结果结构

```json
{
  "rawResponse": "62 F1 30 01 2C 00 64",
  "resultItems": [
    {
      "name": "转速",
      "rawValue": 300,
      "value": 75,
      "unit": "rpm",
      "formula": "x/4",
      "passed": true
    },
    {
      "name": "温度",
      "rawValue": 100,
      "value": -30,
      "unit": "°C",
      "formula": "x*0.1-40",
      "passed": true
    }
  ],
  "resultText": "PASS"
}
```

### 12.3 文件路径规则

建议支持：

- 工作流文件同目录；
- `Workflows/DecodeProfiles/`；
- 工程配置目录；
- 禁止任意绝对路径访问，避免安全和部署问题。

## 13. 与现有 EonTest 代码的落地点

### 13.1 新增基础设施模块

建议新增：

```text
Infrastructure/include/eon/infra/ResponseDecoder.h
Infrastructure/src/ResponseDecoder.cpp
Infrastructure/include/eon/infra/DecodeTypes.h
```

职责：

- 解析 `DecodeSpec`；
- 校验 offset/length；
- 提取字节；
- 按 endian 转换；
- 处理 signed/unsigned；
- 处理 float；
- 处理 string；
- 处理 bits；
- 执行安全公式；
- 返回 `DecodeResult`。

### 13.2 DoIP 插件

现有 [DoipMasterPlugin.cpp](../Plugins/DoipMaster/src/DoipMasterPlugin.cpp) 保持通信职责：

```text
连接
→ Routing Activation
→ 发送 UDS
→ 接收并解析 DoIP
→ 得到 UDS response
→ 调用 ResponseDecoder
→ 写入 context.data
```

不在 DoIP 插件中编写 DID 特例。

建议写入：

```text
rawResponseHex
measuredValue
measuredUnit
measurementName
measuredSamples
resultItems
```

### 13.3 Modbus 插件

现有 Modbus 插件在完成 Modbus 帧解析后，输出统一 Payload，再调用同一 `ResponseDecoder`。

Modbus 插件只负责：

- 站号；
- 功能码；
- 寄存器地址；
- CRC/MBAP；
- 响应错误码。

### 13.4 CAN 插件

CAN 插件负责：

- CAN ID 过滤；
- 帧接收；
- ISO-TP 重组；
- UDS 或应用协议解析。

之后调用同一 `ResponseDecoder`。

### 13.5 串口插件

RS232/RS485 插件负责：

- COM 端口；
- 波特率；
- 数据位；
- 停止位；
- 校验位；
- 终止符或长度组帧。

之后调用同一 `ResponseDecoder`。

### 13.6 LIN、I2C、USB、SPI

这些接口需要各自实现协议适配器，但统一输出 `NormalizedResponse`，不重复实现数据转换逻辑。

## 14. WorkflowEngine 与结果事件改造

当前 `WorkflowEngine` 已经会透传：

- `measuredValue`；
- `measuredUnit`；
- `measurementName`；
- DoIP TX/RX；
- limits；
- `resultText`。

建议增加：

```text
rawResponseHex
rawValue
formula
resultItems
measurementCount
```

`activity.finished` 示例：

```json
{
  "event": "activity.finished",
  "stepId": "step.10",
  "pluginId": "doip.master",
  "rawResponseHex": "62 F1 05 0B B8",
  "measurementName": "发动机转速",
  "measuredValue": 750,
  "measuredUnit": "rpm",
  "rawValue": 3000,
  "formula": "x/4",
  "resultText": "PASS"
}
```

多值时：

```json
{
  "measurementCount": 2,
  "resultItems": [
    {"name": "转速", "value": 750, "unit": "rpm"},
    {"name": "温度", "value": 25.0, "unit": "°C"}
  ],
  "resultText": "PASS"
}
```

失败事件也应透传：

- `rawResponseHex`；
- `doipTx` / `doipRx` 或统一 TX/RX；
- `decodeError`；
- `expectedPrefix`；
- `actualValue`；
- `formula`。

这样解码失败或限值失败时可以直接定位问题。

## 16. 配置优先级

建议配置优先级：

```text
步骤参数 > 解码 Profile 文件 > 协议默认值 > 系统默认值
```

例如：

1. Excel 明确写 `endian=little`，优先使用；
2. Excel 未写，但 Profile 写 `little`，使用 Profile；
3. 都未写，使用协议默认值；
4. 都没有，使用通用默认值 `big`。

通信参数和解码参数必须分开管理：

### 连接参数

## 19. 兼容性策略

为了兼容现有工作流，解码配置全部采用可选字段。

没有以下字段时：

```text
valueOffset
valueLength
valueType
formula
```

默认行为：

```text
measuredValue = 原始 HEX 字符串
measuredUnit = hex
```

因此现有配置：

```text
udsPayload=10 01,expectedPrefix=50 01
```

仍然有效，不需要立即修改。

逐步迁移示例：

### 旧配置

```text
udsPayload=22 F1 05,expectedPrefix=62 F1 05
```

### 新配置

```text
udsPayload=22 F1 05,expectedPrefix=62 F1 05,valueOffset=3,valueLength=2,valueType=uint16,endian=big,formula=x/4
```

## 20. 错误处理规范

所有错误都必须包含足够上下文。

示例：

```text
Decode failed: offset=3 length=4 exceeds payload size=5.
```

```text
Decode failed: float32 requires length=4, actual length=2.
```

```text
Formula failed: division by zero in 'x/0'.
```

```text
Formula failed: unsupported token 'system'.
```

```text
String decode failed: unsupported encoding 'gbk'.
```

错误结果应包含：

- protocol；
- stepId；
- request；
- rawResponseHex；
- decode config；
- 错误原因。

不得把错误静默转换成：

```text
0
0.0
空字符串
PASS
```

## 21. 安全和可靠性要求

1. 公式引擎禁止任意代码执行；
2. Profile 文件只能从允许目录加载；
3. 限制单次解码最大长度；
4. 限制公式最大长度和运算深度；
5. 解码器不得修改原始响应；
6. 协议插件和解码器之间使用只读 Payload；
7. 多线程长连接发送必须使用会话 I/O 锁；
8. 测量结果必须包含原始值，便于追溯；
9. 所有转换都要保留类型和单位；
10. 配置错误必须在执行前尽量校验。

## 23. 结论

这套方案可以覆盖所有通信接口，但前提是每个接口完成自己的协议适配和 Payload 输出：

```text
不同接口、不同协议
        ↓
各自完成连接、组帧、协议校验
        ↓
统一输出 NormalizedResponse.payload
        ↓
所有接口共享 ResponseDecoder
        ↓
统一完成截取、类型转换、公式、限值和报告
```

最终新增测量项的成本应从：

```text
修改 C++ 通信插件 + 重新编译
```

降低为：

```text
增加 Excel 参数或 JSON Decode Profile
```

实施顺序建议严格遵循：

```text
ResponseDecoder 基础能力
→ 公式引擎
→ DoIP 接入
→ Modbus 接入
→ CAN/串口接入
→ 多测量项 Profile
→ LIN/I2C/USB/SPI 接入
```

这样既能保持现有 DoIP 长连接功能稳定，又能逐步把同一套测量和解码能力推广到整个 EonTest 通信体系。
